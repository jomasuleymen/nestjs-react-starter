# Руководство по разработке

Этот файл — единственный источник правил разработки для проекта. Все изменения
должны соответствовать ему. Если запрос пользователя противоречит этому
руководству, сначала явно обозначьте противоречие и предложите безопасное
решение; не нарушайте правило молча.

## Контекст проекта

Стек:

- React 19, TypeScript в строгом режиме и Vite;
- Ant Design 6 и Ant Design Icons;
- TanStack Router, Query, Form и devtools;
- `@hey-api/openapi-ts`, Zustand, Dayjs, Zod, es-toolkit, imask/react-imask,
  clsx и react-error-boundary.

Работайте как опытный frontend-инженер: сначала изучайте контекст, затем
делайте минимальное корректное изменение. Приоритеты: корректность, типовая
безопасность, UX, согласованность, простота, поддерживаемость и производительность.

## Рабочий процесс

Перед нетривиальным изменением:

1. Изучите модуль, сценарий и существующую реализацию.
2. Найдите аналогичные компоненты, запросы и паттерны в проекте.
3. Определите затронутые типы, маршруты, API и общие компоненты.
4. Выберите наименьшее связное изменение, сохраняющее текущую архитектуру.

Не делайте несвязанные рефакторинги, косметические переписывания или новые
абстракции без повторного подтверждённого случая использования. Не добавляйте
зависимости без явного согласования. Не меняйте публичные контракты без
согласования. После изменения запускайте релевантную проверку (например, type
check, lint или build) и честно сообщайте её результат. Тесты не создавайте,
если это не было явно запрошено.

## Именование файлов и экспортов

Имя файла отражает его основной экспорт. Не смешивайте PascalCase, camelCase и
kebab-case без причины.

| Назначение      | Формат файла                  | Примеры                                         |
| --------------- | ----------------------------- | ----------------------------------------------- |
| React-компонент | PascalCase                    | `UserCard.tsx`, `LoginForm.tsx`                 |
| Layout          | PascalCase                    | `AppLayout.tsx`, `DashboardLayout.tsx`          |
| Страница        | PascalCase с суффиксом `Page` | `DashboardPage.tsx`, `LoginPage.tsx`            |
| Контекст        | PascalCase                    | `AuthContext.tsx`, `ThemeContext.tsx`           |
| Provider        | PascalCase                    | `AuthProvider.tsx`, `ThemeProvider.tsx`         |
| Hook            | camelCase                     | `useAuth.ts`, `useBreakpoint.ts`                |
| Сервис          | camelCase                     | `authService.ts`, `reportService.ts`            |
| API-модуль      | camelCase                     | `authApi.ts`, `userApi.ts`                      |
| Утилита         | camelCase                     | `formatCurrency.ts`, `downloadFile.ts`          |
| Типы            | camelCase                     | `user.ts`, `auth.ts`                            |
| Схема           | camelCase                     | `loginSchema.ts`, `profileSchema.ts`            |
| Константы       | camelCase                     | `routes.ts`, `permissions.ts`, `breakpoints.ts` |
| Barrel-файл     | только `index.ts`             | `index.ts`                                      |

React-компоненты всегда называются PascalCase, а их файл совпадает с именем
экспортируемого компонента. Все остальные обычные файлы используют camelCase.
Типы, интерфейсы, классы, enum и React-компоненты внутри файлов используют
PascalCase; функции, переменные и hooks — camelCase.

Исключения допустимы только там, где имя задаёт инструмент или стабильный URL:
TanStack Router-файлы `__root.tsx`, `route.tsx`, `index.tsx`, pathless-layout
`_protected/route.tsx`, группирующие каталоги `(group)`, игнорируемые служебные
файлы `-*.ts` и route-сегменты с kebab-case, если они определяют существующий
публичный URL (например, `no-access.tsx`). Не переименовывайте Vite declaration
file `vite-env.d.ts`, generated-файлы и файлы, на которые по фиксированному пути
ссылается генератор; текущий пример — `src/api/http/generated-client-config.ts`
для OpenAPI-клиента.

## Архитектура

Используйте прагматичную модульную архитектуру с колокацией и тонкими
маршрутами. Это не FSD, Clean Architecture, Atomic Design и не техническая
слоистая архитектура.

- `src/app` — композиция приложения: провайдеры, layouts, настройка router и
  QueryClient, глобальная конфигурация и стили.
- `src/routes` — файловые TanStack Router-маршруты и только routing concerns.
- `src/modules` — изолированные бизнес-модули и возможности приложения.
- `src/api/generated` — генерируемый Swagger-клиент; не редактировать вручную.
- `src/api/http` — HTTP-транспорт, interceptors, обновление токена и
  нормализация API-ошибок.
- `src/shared` — переиспользуемые, бизнес-нейтральные компоненты, hooks,
  утилиты и типы.
- `src/assets` — глобально используемые ассеты, обрабатываемые Vite.
- `public` — файлы со стабильными публичными URL, не обрабатываемые Vite.

Модуль создаёт только нужные каталоги: `api`, `adapters`, `components`, `pages`,
`model`, `hooks`, `assets`. Не создавайте пустые каталоги.

Разрешённые зависимости:

- `app` может импортировать `routes`, `modules`, `api` и `shared`;
- `routes` — `modules`, `app/layouts` и `shared`;
- `modules` — `api/generated`, `api/http` и `shared`;
- `shared` не импортирует из `modules`, `routes` или `app`;
- `api` не импортирует из `modules`, `routes` или `app`;
- `modules` не импортируют из `routes` или `app`;
- generated API-код не импортирует код приложения.

Не допускайте циклических зависимостей. Межмодульные импорты разрешены только
через публичный API модуля.

## Маршруты, страницы и layouts

Файлы маршрутов остаются тонкими: путь и параметры, валидация search-параметров,
guards, redirects, loaders, предварительная загрузка запросов и передача
route-state/навигационных callbacks странице. Бизнес-логика и страницы живут в
`src/modules`, а не в `src/routes`.

Один простой маршрут может быть плоским. При нескольких routing concerns
используйте папку с `route.tsx`, `index.tsx` и соседними route-файлами. `(group)`
используется только для организации файлов, без изменения URL и дерева
компонентов. Все защищённые маршруты — потомки pathless layout
`_protected/route.tsx`.

Маршрут с проверкой прав обязан объявлять `createRouteAccessGuard(...)` в
`beforeLoad`, даже если пункт навигации скрыт. Скрытая навигация не является
авторизационной границей. Права и правила доступа импортируйте из публичного API
auth-модуля; не дублируйте строки прав в маршрутах и компонентах.

Pages координируют пользовательский сценарий: собирают module-компоненты,
показывают состояния query и выполняют действия страницы. Layouts отвечают за
общую структуру экрана и навигацию, а не за бизнес-логику или загрузку данных
конкретной страницы. Держите layout-компоненты переиспользуемыми и передавайте
область содержимого через `children` или явные compositional slots.

## Компоненты и повторное использование

Один компонент должен иметь ясную основную ответственность. Страница композиционно
собирает крупные блоки, а повторяющаяся логика выделяется в hook, утилиту или
компонент только после появления реальной общей потребности. Предпочитайте
композицию наследованию: используйте props, `children`, slots и небольшие
сфокусированные компоненты вместо иерархий базовых классов или универсальных
компонентов с множеством несвязанных флагов.

Сначала используйте существующие shared- и module-компоненты. Код становится
`shared` только когда он действительно бизнес-нейтрален и нужен нескольким
модулям. Не копируйте бизнес-правила, схемы, query keys, форматирование или
состояния интерфейса: вынесите общий источник в наиболее узкий подходящий слой.

## Состояние и данные

- TanStack Query владеет server state и его cache.
- TanStack Router search params владеют URL-состоянием, которым можно поделиться.
- Библиотеки форм владеют form state; локальное UI-state принадлежит компоненту.
- Zustand хранит только действительно кросс-страничное клиентское состояние,
  включая аутентифицированную сессию.
- Не копируйте query-, URL- или form-state в Zustand.
- Access token хранится только в памяти HTTP-слоя, никогда не в Zustand и не в
  Web Storage.

Используйте сгенерированный API-клиент как расходный код и оборачивайте его
модульными query/mutation options. Не смешивайте транспортный код с UI.

## TypeScript

TypeScript всегда остаётся в strict-режиме. Не используйте `any`; если без него
временно нельзя обойтись, зафиксируйте причину и ограничьте область применения.
Предпочитайте точные типы, type guards, Zod-схемы и безопасную обработку
неизвестных данных. Не подавляйте ошибки типов без понимания причины и не
ослабляйте настройки TypeScript ради прохождения проверки.

## UI, Ant Design и стили

Используйте один корневой Ant Design `ConfigProvider` и глобальные theme tokens
для цветов, типографики, отступов, радиусов и component defaults. До создания
кастомного UI проверьте, подходит ли документированный компонент Ant Design.

Для Ant Design предпочитайте tokens, затем документированные `styles` и
`classNames`. Inline `style` допустим только для небольших локальных layout-
настроек; цвета и тени берите из `theme.useToken()`, а не дублируйте literals.
Не добавляйте Tailwind, глобальные stylesheet overrides,
селекторы `.ant-*` и новые импорты `.scss`, `.sass` или `.less`.
CSS Modules/SCSS возможны только после явного архитектурного решения для сложного
локального UI, который нельзя поддерживаемо выразить tokens и документированными
API Ant Design.

## Accessibility и responsive design

Каждый экран должен быть полноценно usable на mobile и desktop. Проектируйте от
доступного узкого viewport к широкому: не полагайтесь только на фиксированные
размеры, не допускайте горизонтального скролла для обычного контента и сохраняйте
доступ ко всем основным действиям на малых экранах.

Используйте нативные семантические элементы, когда они подходят. У интерактивных
элементов должны быть понятные accessible names, видимый keyboard focus, ожидаемая
tab-навигация и управление с клавиатуры. Не заменяйте `button`/`a` на `div` без
необходимой семантики и обработки клавиатуры. Для изображений задавайте корректный
`alt`, а для форм — связанный label, текст ошибки и понятное состояние required.
Проверяйте контраст, состояния loading/empty/error/permission и сообщения,
понятные пользователю.

## Значимые UX-задачи

Для новых экранов или существенных пользовательских сценариев до реализации
кратко определите: проблему и пользователей, информационную архитектуру и flow,
состояния экранов и компонентов, loading/empty/error/permission-состояния,
краевые случаи и UX-компромиссы.

## Границы изменений

Сохраняйте существующее поведение, если задача явно не требует другого. Не
дублируйте бизнес-логику, не оптимизируйте без измеримого основания и не
изобретайте новый архитектурный паттерн, когда подходит существующий. При
неоднозначности выбирайте наименьшее разумное решение и явно сообщайте допущение.
Для рискованных изменений (аутентификация, сессии, платежи, миграции, схемы,
динамические запросы) сначала объясните влияние и компромиссы.
